# Walico 実装ロジック設計書

## 1. ログイン不要の実装アプローチ

### 1.1 基本的な設計思想

**ログイン不要を実現するための核心設計：**

1. **URL ベースのアクセス制御**

   - 各トランザクションに UUID を発行
   - URL（`/r/[uuid]`）を知っている人だけがアクセス可能
   - これは実質的な「暗黙の認証」として機能

2. **ステートレスな設計**
   - ユーザー情報を一切保持しない
   - トランザクションデータのみを一時的に保存
   - 期限切れデータは自動削除

### 1.2 セキュリティ上の考慮事項

#### [ ] 実装可能な点

1. **トランザクション作成**

   - 誰でも作成可能（問題なし）
   - UUID は十分にランダム（推測不可能）

2. **トランザクション閲覧**

   - URL を知っている人だけが閲覧可能
   - レシート画像も同様に URL ベースでアクセス

3. **支払い完了の更新**
   - URL を知っている人（信頼できる関係者）が更新可能
   - 一度「支払い済み」になったら元に戻せない仕様（誤操作防止）

#### ⚠️ 注意が必要な点

1. **支払い完了の不正更新リスク**

   - 誰でも URL を知っていれば「支払い済み」に変更できてしまう
   - **対策**:
     - URL を LINE で共有するため、基本的に信頼できる関係者のみ
     - 一度「支払い済み」になったら変更不可とする

2. **データの有効期限**
   - 一定期間（7 日など）後に自動削除またはアクセス不可にする
   - Cloudflare R2 の画像も同様にライフサイクルポリシーで削除

## 2. データフロー設計

### 2.1 トランザクション作成フロー

```
1. ユーザーがレシートを撮影/入力
   ↓
2. フロントエンド: データを準備（店名、金額、割り勘比率など）
   ↓
3. API Route: POST /api/transactions
   - UUIDを生成（crypto.randomUUID()）
   - Tursoにデータを保存
   - Cloudflare R2に画像をアップロード（既にアップロード済みの場合、URLを受け取る）
   ↓
4. レスポンス: { id: "uuid", url: "/r/uuid" }
   ↓
5. フロントエンド: LINEアプリを起動（URLスキーム）
   - テキスト: 「[店名]の代金 ¥[請求額] お願い！ レシート詳細: https://walico.app/r/[uuid]」
```

### 2.2 トランザクション閲覧フロー

```
1. ユーザーがURLにアクセス: /r/[id]
   ↓
2. API Route: GET /api/transactions/[id]
   - UUIDでトランザクションを検索
   - 有効期限チェック（expires_at）
   - データを返す
   ↓
3. フロントエンド: データを表示
```

### 2.3 支払い完了フロー

```
1. ユーザーが「支払いを完了する」ボタンをクリック
   ↓
2. API Route: PATCH /api/transactions/[id]/status
   - UUIDでトランザクションを検索
   - status が 'pending' の場合のみ 'paid' に更新
   - 既に 'paid' の場合はエラー（更新不可）
   ↓
3. フロントエンド: 状態を更新し、ボタンを無効化
```

### 3.2 API 仕様

#### POST /api/transactions

**Request Body:**

```typescript
{
  store_name: string | null;
  total_amount: number;
  request_amount: number;
  receipt_image_url: string | null;
  items_json: Array<{ name: string; price: number }> | null;
}
```

**Response:**

```typescript
{
  id: string; // UUID
  url: string; // /r/[id]
}
```

#### GET /api/transactions/[id]

**Response:**

```typescript
{
  id: string;
  store_name: string | null;
  date: string; // ISO 8601形式
  total_amount: number;
  request_amount: number;
  receipt_image_url: string | null;
  items_json: Array<{ name: string; price: number }> | null;
  status: "pending" | "paid";
  created_at: number; // Unix timestamp
  expires_at: number; // Unix timestamp
}
```

#### PATCH /api/transactions/[id]/status

**Request Body:**

```typescript
{
  status: "paid";
}
```

**Response:**

```typescript
{
  id: string;
  status: "paid";
}
```

**エラーケース:**

- 404: トランザクションが見つからない
- 400: 既に支払い済み（status === 'paid'）
- 410: 有効期限切れ（expires_at < 現在時刻）

## 4. データベース設計（Turso/SQLite）

### 4.1 マイグレーション

```sql
CREATE TABLE IF NOT EXISTS transactions (
  id TEXT PRIMARY KEY,
  store_name TEXT,
  total_amount INTEGER NOT NULL,
  request_amount INTEGER NOT NULL,
  receipt_image_url TEXT,
  items_json TEXT,  -- JSON文字列として保存
  status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'paid')),

-- 有効期限切れデータの自動削除用（定期実行が必要）
```

## 7. セキュリティ対策のまとめ

### 7.1 URL ベースのアクセス制御で十分な理由

1. **UUID の推測不可能性**

   - crypto.randomUUID()は 128 ビットのランダム値
   - 推測確率は実質的に 0

2. **URL の共有経路**

   - LINE 経由で信頼できる関係者にのみ共有
   - URL を知っている=信頼できる関係者と見なせる

3. **データの一時性**
   - 7 日後には自動削除またはアクセス不可
   - 長期にわたるリスクが低い

### 7.2 追加で検討できる対策（オプション）

1. **レート制限**

   - IP アドレスベースのレート制限
   - 同じ UUID からの過度なリクエストを制限

2. **支払い完了時の確認**

   - 「本当に支払いを完了しましたか？」確認モーダル
   - 誤操作防止

3. **アクセスログ**
   - どの URL にアクセスがあったかログ記録
   - 不正アクセスの検知（ただし、ユーザー情報は保持しない）

## 8. ログイン機能の実装フロー

### 8.1 概要

ログイン機能を追加することで、以下の課題を解決します：

- **デバイス間での履歴共有**: LocalStorage ではなくサーバー側で履歴を管理
- **送信者・受信者の管理**: 誰から請求されたか、誰に請求したかを記録
- **合計金額の自動計算**: 複数の請求の合計を自動計算
- **受け取った請求の一覧**: LINE のトーク画面以外でも確認可能

### 8.2 認証方式

**LINE ログインを採用**

- LINE アプリとの親和性が高い
- 既存の LINE 連携フローと自然に統合できる
- ユーザーが LINE アカウントでログイン

**環境変数:**

```env
LINE_CHANNEL_ID=...
LINE_CHANNEL_SECRET=...
BETTER_AUTH_SECRET=...  # ランダムな文字列（openssl rand -base64 32）
BETTER_AUTH_URL=https://walico.app  # アプリのベースURL
```

### 8.3 データベース設計の拡張

#### 8.3.1 ユーザーテーブルの追加（better-auth 統合）

better-auth は自動的に必要なテーブル（user, session, account, verification 等）を作成しますが、LINE ユーザー ID を保存するためにカスタムフィールドを追加します。

**Drizzle スキーマ:**

```typescript
// src/libs/db/schema.ts
import { sqliteTable, text, integer, index } from "drizzle-orm/sqlite-core";

// better-authの基本テーブル（自動生成されるが、カスタマイズ可能）
export const user = sqliteTable("user", {
  id: text("id").primaryKey(),
  name: text("name"),
  email: text("email").unique(),
  emailVerified: integer("email_verified", { mode: "boolean" }),
  image: text("image"),
  createdAt: integer("created_at").notNull(),
  updatedAt: integer("updated_at").notNull(),
  // カスタムフィールド: LINEユーザーID
  lineUserId: text("line_user_id").unique(),
});

// LINEアカウント連携用（better-authのaccountテーブルを拡張）
export const account = sqliteTable("account", {
  id: text("id").primaryKey(),
  userId: text("user_id").notNull().references(() => user.id),
  providerId: text("provider_id").notNull(), // "line"
  providerAccountId: text("provider_account_id").notNull(), // LINEユーザーID
  accessToken: text("access_token"),
  refreshToken: text("refresh_token"),
  expiresAt: integer("expires_at"),
  createdAt: integer("created_at").notNull(),
  updatedAt: integer("updated_at").notNull(),
});

CREATE INDEX IF NOT EXISTS idx_user_line_user_id ON user(line_user_id);
CREATE INDEX IF NOT EXISTS idx_account_user_id ON account(user_id);
CREATE INDEX IF NOT EXISTS idx_account_provider ON account(provider_id, provider_account_id);
```

**注意:** better-auth はマイグレーションを自動生成する機能もあるため、既存の Drizzle マイグレーションと統合する必要があります。

#### 8.3.2 トランザクションテーブルの拡張

```sql
-- 既存のtransactionsテーブルにカラムを追加
ALTER TABLE transactions ADD COLUMN sender_id TEXT REFERENCES users(id);
ALTER TABLE transactions ADD COLUMN recipient_line_id TEXT;  -- LINE ID（ログイン前でも使える）

-- インデックス追加
CREATE INDEX IF NOT EXISTS idx_transactions_sender_id ON transactions(sender_id);
CREATE INDEX IF NOT EXISTS idx_transactions_recipient_line_id ON transactions(recipient_line_id);
```

### 8.4 認証フロー

#### 8.4.1 LINE ログインフロー（better-auth）

```
1. ユーザーが「ログイン」ボタンをクリック
   ↓
2. フロントエンド: better-authクライアントでLINEログインを開始
   - authClient.signIn.social({ provider: "line" })
   ↓
3. better-authがLINE認証サーバーにリダイレクト
   - ユーザーがLINEアカウントで認証
   ↓
4. LINE認証サーバーからコールバック: /api/auth/callback/line
   - better-authが自動処理
   ↓
5. better-auth: codeをaccess_tokenに交換
   - LINE API: POST https://api.line.me/oauth2/v2.1/token
   ↓
6. better-auth: access_tokenでユーザー情報を取得
   - LINE API: GET https://api.line.me/v2/profile
   ↓
7. better-auth: データベースにユーザー情報を保存/更新
   - line_user_idで既存ユーザーを検索
   - 存在しない場合は新規作成
   ↓
8. better-auth: セッションを作成
   ↓
9. フロントエンド: ダッシュボードにリダイレクト
```

#### 8.4.2 セッション管理（better-auth）

**better-auth を使用**

better-auth は Drizzle ORM と統合しやすく、既存のデータベーススキーマと連携できます。

**サーバー側設定:**

```typescript
// src/libs/auth.ts
import { betterAuth } from "better-auth";
import { drizzleAdapter } from "better-auth/adapters/drizzle";
import { db } from "@/libs/db";
import * as schema from "@/libs/db/schema";

export const auth = betterAuth({
  database: drizzleAdapter(db, {
    provider: "sqlite",
    schema: schema, // Drizzleスキーマを指定
  }),
  baseURL: process.env.BETTER_AUTH_URL,
  secret: process.env.BETTER_AUTH_SECRET,
  socialProviders: {
    line: {
      clientId: process.env.LINE_CHANNEL_ID!,
      clientSecret: process.env.LINE_CHANNEL_SECRET!,
      scope: ["profile", "openid"], // LINEログインに必要なスコープ
    },
  },
  // カスタムユーザースキーマとの統合（オプション）
  user: {
    additionalFields: {
      lineUserId: {
        type: "string",
        required: false,
      },
    },
  },
});
```

**API Route:**

```typescript
// src/app/api/auth/[...all]/route.ts
import { auth } from "@/libs/auth";
import { toNextJsHandler } from "better-auth/next-js";

export const { GET, POST } = toNextJsHandler(auth);
```

### 8.5 トランザクション作成フローの拡張

#### 8.5.1 ログイン済みユーザーの場合

```
1. ユーザーがレシートを撮影/入力
   ↓
2. フロントエンド: セッションからユーザーIDを取得
   ↓
3. API Route: POST /api/transactions
   - セッションからsender_idを取得
   - recipient_line_idをオプションで受け取る（LINE ID）
   - トランザクション作成時にsender_idを保存
   ↓
4. レスポンス: { id: "uuid", url: "/r/uuid" }
   ↓
5. フロントエンド: LINEアプリを起動（URLスキーム）
```

#### 8.5.2 ログイン前でも利用可能

- ログインしていない場合、sender_id は null のまま
- 既存の動作（URL ベースのアクセス制御）を維持
- ログイン後に既存のトランザクションと紐付け可能（オプション）

### 8.6 ダッシュボード機能の実装フロー

#### 8.6.1 送った請求一覧の取得

```
1. ユーザーがダッシュボードにアクセス: /dashboard
   ↓
2. フロントエンド: セッションを確認（ログイン必須）
   ↓
3. API Route: GET /api/transactions/sent
   - セッションからユーザーIDを取得
   - sender_idでトランザクションを検索
   - 作成日時の降順でソート
   ↓
4. レスポンス: トランザクション一覧
   ↓
5. フロントエンド: 一覧を表示
   - 店名、請求額、ステータス、作成日時
   - 合計金額を自動計算
```

#### 8.6.2 受け取った請求一覧の取得

```
1. ユーザーがダッシュボードにアクセス: /dashboard
   ↓
2. フロントエンド: セッションを確認（ログイン必須）
   ↓
3. API Route: GET /api/transactions/received
   - セッションからLINEユーザーIDを取得
   - recipient_line_idでトランザクションを検索
   - または、recipient_idで検索（ログイン済みユーザー同士の場合）
   ↓
4. レスポンス: トランザクション一覧（送信者情報を含む）
   ↓
5. フロントエンド: 一覧を表示
   - 送信者名、店名、請求額、ステータス、作成日時
   - 未払い合計金額を自動計算
```

#### 8.6.3 合計金額の計算

```
1. API Route: GET /api/dashboard/summary
   - セッションからユーザーIDを取得
   ↓
2. データベース: 集計クエリを実行
   - 送った請求の合計（pending）
   - 送った請求の合計（paid）
   - 受け取った請求の合計（pending）
   - 受け取った請求の合計（paid）
   ↓
3. レスポンス: 集計結果
   ↓
4. フロントエンド: サマリーを表示
```

### 8.10 既存機能との互換性

- **ログイン前でも利用可能**: 既存の URL ベースのアクセス制御を維持
- **段階的な移行**: ログイン機能はオプションとして実装
- **既存の URL**: `/r/[id]`は引き続き動作（ログイン不要）
- **LocalStorage**: 既存の履歴機能は引き続き動作（ログイン後はサーバー側の履歴を優先）

## 9. 結論

**ログイン不要の要件は実装可能です。**

理由：

- URL ベースのアクセス制御で十分なセキュリティが確保できる
- トランザクション単位でのデータ管理でユーザー情報が不要
- データの一時性により長期リスクが低い
- 信頼できる関係者間での利用という前提が明確

この設計により、「3 秒で完結」「ログイン不要」というコンセプトを実現できます。

**ログイン機能はオプションとして追加可能**で、以下のメリットを提供します：

- デバイス間での履歴共有
- 送信者・受信者の管理
- 合計金額の自動計算
- 受け取った請求の一覧表示

既存の機能を維持しつつ、段階的にログイン機能を追加できます。
